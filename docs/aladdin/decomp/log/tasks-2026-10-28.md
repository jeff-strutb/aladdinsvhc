# Tasks in the oracles, 2026-10-28

## What was built

- Every swapped call's C runs on a libco coroutine from the core's own
  libco. Patch 0015 exports the address of `cpu.thread`; the checker points
  it at the coroutine while the C runs, so the PPU and SMP threads, which
  resume `cpu.thread`, come back to the C.
- `task_yield()` (machine.h) ends a task call's C. In lockstep the call's
  record ends at the scheduler ($81:BC7F, S = $0326) on both sides; the
  coroutine is parked under the task's slot; where the scheduler's RTL lands
  on the slot's resume address with its S, both sides open a record and the
  C goes on. The resume address is read from the task's stack (P, then Y
  and X at the width P gives, D, B, then the JSL's return) the same way on
  both sides, never from the C.
- A5 judges the same pieces: each watch's C on its own coroutine, judged
  at the wait (the registers at the scheduler, the pushes above the saved
  S) and at each resume's end.
- Frame compares judge each task's stack above its own live S.

## Traps met

- The first lockstep run died at once with SIGBUS: the checker stored the
  `dlsym` of the export function as if it were the thread's address and
  wrote into the function's page. Found from the backtrace (a crash handler
  in the hybrid prints it) and the source line (`atos`).
- A script `load` copies the state's S-CPU thread into whatever
  `cpu.thread` points at: the checker puts the S-CPU's own thread back first.

## Results

On every script: TaskWait identical on 241,892 pieces, Wait64Frames on 30,
TaskSlotFree on 200, TaskExit on its unit call; the whole image identical.
Planted bugs fail at the byte they change: a wrong wait count ($0070), a
dropped B push ($0162, a waiting task's stack), a wrong return address
($015C).
